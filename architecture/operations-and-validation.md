# 운영, 복구, 검증 계획

여기에 적힌 검증은 구현 후 수행할 인수 기준이다. 문서 작성 단계에서 수집기·DB·대시보드가 구현되거나 이 기준을 통과했다고 주장하지 않는다. 실제 확인된 입력 점검은 [근거 문서](../proposal/evidence-and-references.md)에 별도로 기록했다.

## 1. 실행 환경과 스케줄

Docker Compose에 PostgreSQL, MongoDB, Streamlit 서비스를 정의하고 Python 배치 실행 이미지를 함께 사용한다. 호스트 cron이 배치를 호출하며, 프로세스 잠금과 PostgreSQL advisory lock으로 동시 작성자를 하나로 제한한다. Streamlit은 읽기 전용 자격 증명을 사용한다. 비밀값은 Git 밖의 환경 설정에 두고 로그와 manifest에서 제거한다.

| 작업 | 기본값 | 완료 기준 |
|---|---|---|
| 소셜 일별 갱신 | 매일 02:00 UTC / 11:00 KST | 최근 7일의 닫힌 UTC 날짜를 조회하고 eligible source의 적재·검증 완료 |
| 선정 웹사이트 확인 | 일별 배치에 포함 | 조건부 요청 또는 해시 비교, 링크 변경 후보 기록 |
| 가격 import | 새 CSV가 들어왔을 때 수동 실행 | 해시·키·기간·숫자 검증 후 current price와 새 build 생성 |
| 월별 재검증 | 매월 15일 03:00 UTC / 12:00 KST | 직전 두 달의 가능한 archive, 링크·삭제 상태 확인, manifest 작성 |
| 백업 | 성공적인 공개 배치 이후 일 1회 | 두 DB와 manifest의 복구 가능한 일치 지점 확보 |

노트북이 꺼져 있으면 cron이 실행되지 않을 수 있다. 시작 시 마지막 완료 구간을 확인해 놓친 날짜를 backfill queue로 넣고 순차 복구한다. 최근 7일만 재조회해 오래된 누락을 방치하지 않는다. 월별 작업도 동일한 잠금을 사용하며 일별 실행과 겹치면 대기한다. Docker/클라우드의 자동 상시 실행을 이미 확보했다고 가정하지 않는다.

초기 scope 설정은 버전이 고정된 registry와 소스 활성 상태로 관리한다. Reddit은 정책 조건이 해결되기 전 disabled다. 활성화된 필수 scope에서 기술 오류가 나면 해당 실행의 새 공개 build를 만들지 않고 이전 결과를 유지한다. 제외된 source와 확인된 역사적 공백은 명시된 unavailable/partial 상태로 표현할 수 있다.

## 2. 적재와 공개 순서

1. `ingestion_runs`에 범위와 설정 버전을 기록하고 상태를 `running`으로 만든다.
2. 응답을 임시 원본 파일에 기록한다. 해시·크기를 검증하고 atomic rename으로 확정한다.
3. `social_observations`를 snapshot ID로 idempotent upsert하고 `social_items`의 현재 상태를 갱신한다. 오래된 fetched_at의 재실행으로 최신 문서를 되돌리지 않는다.
4. 해당 페이지/하위 시간 구간의 MongoDB 쓰기가 모두 확인된 뒤 체크포인트를 확정한다. manifest와 체크포인트는 이미 저장된 artifact를 참조한다.
5. 정해진 snapshot을 읽고 전처리·코인 매칭을 수행한다. PostgreSQL의 `social_features`와 `item_assets`는 item 단위 트랜잭션으로 교체한다. 같은 item의 오래된 매핑이 남지 않게 한다.
6. 가격과 소셜의 고정 입력 manifest를 만들고 새 `build_id`로 `market_daily`와 `social_daily`를 생성한다. 초기 규모에서는 보유 기간 전체를 재집계해 경계·정정 오류를 줄인다.
7. 키 중복, FK, coverage, 지표, 원본·snapshot 추적을 검증한다. 새로운 기술 실패가 있으면 build를 failed로 남긴다. 사전에 기록된 역사 구간의 partial은 null 지표와 함께 허용한다.
8. PostgreSQL 트랜잭션 안에서 build를 published로 바꾸고 `dashboard_state.published_build_id`를 변경한다. 모든 차트 쿼리는 같은 포인터를 사용한다.

전체 run은 `queued → running → succeeded | partial | failed | disabled`로 종료한다. 요청 예산 소진이나 페이지 미완료는 partial이며 성공한 전체 구간의 watermark로 승격하지 않는다. 명시적으로 확인한 역사 데이터 부재와 기술적 미완료는 다른 reason code를 사용한다. build는 `building → validated → published` 또는 `failed/withdrawn` 상태를 갖는다.

PostgreSQL 포인터 변경이 공개의 원자적 경계다. MongoDB·파일 저장소와 분산 트랜잭션을 만들지 않는다. 이미 적재된 관측이 있지만 공개되지 않은 상태는 허용하며, 다음 실행에서 이를 재사용해 복구한다. 최신 문서 탐색과 공개 차트의 기준 시각 차이는 화면에 표시한다.

## 3. 실패, 재시도, 복구

| 상황 | 처리 |
|---|---|
| 연결 오류·5xx | 최대 3회 추가 재시도, 2/4/8초 지수 대기와 jitter; 실패 구간 기록 |
| 429 | Retry-After 또는 공급자가 명시한 reset 시각을 우선. 긴 대기는 다음 실행으로 넘기고 체크포인트 유지 |
| 403·권한 거부 | source job을 failed로 종료하고 blocked_access 사유 표시. 우회하지 않음 |
| 404·빈 결과 | 즉시 삭제/0건으로 단정하지 않음. endpoint와 응답 의미를 확인하고 불확실하면 partial |
| Arctic Shift timeout/422 | 허용된 query인지 확인 후 시간 구간 분할. 동일한 큰 쿼리의 무한 재시도 금지 |
| cursor 반복·응답 schema 변경 | 원본과 진단 보존, parser 격리, 구간 완료 처리 금지 |
| raw 저장 후 MongoDB 실패 | 확정된 raw에서 재실행. 체크포인트를 앞당기지 않음 |
| MongoDB 적재 후 PostgreSQL 실패 | snapshot ID에서 파생 투영·build만 재생성. 원격 재수집 불필요 |
| 공개 직전 프로세스 종료 | 미공개 build는 화면에 보이지 않음. 검증 후 공개하거나 실패로 정리 |
| MongoDB 일시 장애 | 차트는 기존 PostgreSQL build 유지; 상세는 조회 불가 표시 |
| 디스크 부족·백업 실패 | 새 수집/공개 중단, 마지막 성공 결과 유지, Data health에 상태 표시 |

이전 성공 build가 없으면 빈 차트에 데이터를 만들어 넣지 않고 “아직 수집·공개된 데이터 없음”을 표시한다. 실패한 source를 정상인 것처럼 숨기지 않는다. 원격 데이터가 달라진 재수집과 같은 입력의 재처리는 구별하며, 동일 artifact 재처리에서 item·snapshot 중복이 생기지 않아야 한다.

## 4. 백업, 삭제, 접근 관리

배치 작성자를 잠시 멈춘 동일 지점에서 PostgreSQL dump, MongoDB dump, registry와 archive manifest를 묶어 백업한다. 아카이브 원문은 증분 복사하고 checksum 목록으로 확인한다. 초기 기본값은 일별 백업 14세대이며 소스별 더 짧은 보관 조건이 우선한다. 월별 manifest는 정기 백업을 대체하지 않는다.

첫 통합 실행 이후 별도 빈 볼륨에 복구한다. 두 DB의 연결 ID, 공개 build, manifest와 원본 해시가 일치하는지 확인한다. 백업 목표는 **마지막 성공 배치까지 복구 가능**한 상태이며, 실제 측정 전에는 RPO/RTO를 달성했다고 표현하지 않는다.

소셜 본문과 원본 응답의 초기 보관 기본값은 프로젝트 종료 후 30일 이내 삭제다. 사용 조건이 더 짧으면 그 기준을 적용한다. 사용자·플랫폼 삭제 요청이나 확인된 삭제 표지가 있으면 정기 보관 만료까지 기다리지 않고 처리한다. 날짜가 정해지면 retention 종료일을 설정 파일에 고정한다.

삭제 처리 순서는 원문 표시 차단 → MongoDB 본문·payload 제거 → PostgreSQL 텍스트 해시·파생값·매핑 정리 → 영향 build 철회 및 재생성 → 원본 artifact와 백업 처리다. 같은 raw 응답에 여러 게시물이 들어 있어 개별 삭제가 불가능하면 그 응답 파일 전체를 제거하고 manifest에 사유를 기록한다. 본문을 제거한 파일을 원본과 동일하다고 표시하지 않는다. 관련 백업 세대도 정리하고 정리된 상태로 새 백업을 만든다.

현재 공개 build가 삭제의 영향을 받으면 같은 트랜잭션에서 공개 포인터를 null로 바꾼다. 정리된 새 build가 검증될 때까지 관련 분석을 일시 비공개로 표시하고, 삭제된 콘텐츠를 포함할 수 있는 과거 build로 자동 복귀하지 않는다.

삭제된 원문을 재처리로 되살리지 않도록 최소 tombstone을 유지한다. 보관할 수 있는 식별 정보의 범위는 해당 소스 조건에 맞추며 본문을 tombstone에 복사하지 않는다. 영향받은 build는 복구·재공개 대상에서 제외한다. 요청 실패만으로 삭제됐다고 단정하지 않는다.

팀 내부 접근을 기본으로 하고 외부 공개 시에는 원문 재배포 범위를 다시 확인한다. 원본 payload는 다운로드 링크로 무조건 노출하지 않는다. 수집 대상과 무관한 이용자 프로파일링·신원 추론은 하지 않는다.

## 5. 검증 시나리오와 인수 기준

| 영역 | 시나리오 | 기대 결과 |
|---|---|---|
| 입력 데이터 | 첨부 ZIP import | 10개 파일, 14,773행, 공통 기간·품질 수치가 근거 문서와 일치 |
| 멱등성 | 같은 raw page와 run을 두 번 적재 | item·observation 중복 없음; 집계 값 동일 |
| 새로운 관측 | 같은 item의 다음날 반응 수 변경 | item은 하나, observation은 추가; 시각과 출처 유지 |
| 페이지 경계 | 같은 초의 100개 이상 결과, 반복 cursor | 누락 없이 분할·dedup하거나 partial 명시; 성공으로 위장하지 않음 |
| 시간 | UTC 자정 전후·다른 시간대 입력 | 올바른 event_date, 중복/누락 없는 반열림 범위 |
| 코인 식별 | 동명 ticker, Solana 대소문자, native DOGE | 서로 다른 자산 혼합 방지; 모호한 매칭은 미확정 |
| 원작성자 | 선정 계정 타임라인의 다른 작성자 재게시 | 선정 계정의 직접 게시 건수에서 제외 |
| 누락 | 실패 응답, 정상 빈 응답, 부분 역사 | failed/null, scope 확인 후 0, partial을 구별 |
| DB 경계 | MongoDB 성공 후 SQL 실패 | 마지막 공개 build 유지; snapshot으로 재처리 가능 |
| 추적 | 차트의 코인·날짜에서 표본 게시물 추적 | asset/item/snapshot/run/raw URI·해시를 연결 |
| JOIN | 여러 게시물이 같은 가격일에 연결 | 가격 행·거래량 중복 합산 없음 |
| 삭제 | 이미 공개한 item의 삭제 확인 | 원문 비노출, 파생 결과 재계산, 백업 복구로 재등장 방지 |
| 모델 변경 | 같은 raw에 새 parser·매칭 규칙 적용 | 새 버전·build로 분리, 기존 결과와 비교 가능 |
| 통계 | 상수열·30일 미만·누락일·0 가격 | 정의되지 않은 수익률/상관/변동성은 null |
| 애플리케이션 | DB 일부 중단, source 비활성, 오래된 가격 | 차트·상세의 가용 범위를 분리하고 마지막 갱신 시각 표시 |

검증 fixture는 작은 합성 응답과 사용 가능한 실제 표본을 구분해 관리한다. 실제 플랫폼 정책을 위반하는 데이터를 테스트라는 이유로 새로 수집하지 않는다. 단위 검증은 parser·키·날짜·집계에 집중하고, 통합 검증은 raw → MongoDB → PostgreSQL → 화면 흐름과 복구에 집중한다.

## 6. 분석 품질과 성능 평가

코인·플랫폼·매칭 유형별로 층화한 최대 200개 item을 수작업 검토한다. eligible item이 더 적으면 전부 검토하고 실제 표본 수를 보고한다. 명시적 언급·문맥 연결·무관·모호함을 구별한 라벨로 precision과 오류 유형을 보고한다. 알려진 수집 표본 밖의 전 플랫폼 recall을 주장하지 않는다.

영어 감성은 긍정·중립·부정·판단 불가로 검토한다. 풍자, 금융 문맥, emoji, 홍보성 반복의 오류 예시를 기록한다. Cohen's kappa 등 다중 평가자 일치도는 실제로 두 명 이상이 독립 라벨링한 경우에만 보고한다. 감성의 좋고 나쁨을 가격 방향 예측 성능과 혼동하지 않는다.

차트 조회 목표는 PostgreSQL 주요 쿼리의 warm-cache p95 2초 이내다. 주요 화면별 쿼리를 대표 코인·기간으로 30회 측정하고 하드웨어, DB 버전, 인덱스, row 수, 기간, cold-cache 최초 실행값을 함께 기록한다. end-to-end 화면 시간은 별도로 측정한다. 목표를 못 맞추면 실행 계획으로 집계·인덱스를 수정한다.

실제 데이터 규모와 합성 부하 규모를 분리한다. 현재 가격 14,773행만으로 대규모 처리 성능을 증명하지 않는다. 소셜 데이터의 확보량·저장 크기·일별 처리 시간·실패율을 보고하고 강의의 규모 기대치는 별도로 확인한다. 사용 가능한 데이터가 적어도 실패·복구·모델링의 정확성을 먼저 평가한다.

## 7. 6주 실행 계획

| 주 | 작업과 산출물 | 통과 조건 |
|---|---|---|
| 1 | source/access registry, asset 매핑, schema, 샘플 fixture | 각 source의 활성/비활성 사유와 DB 책임 확정 |
| 2 | 가격 import, eligible social collector, raw archive, checkpoint | 작은 구간의 반복 수집과 중단 복구 |
| 3 | MongoDB 모델, 텍스트 처리, SQL 투영·mart·공개 포인터 | 고정 입력에서 동일 결과와 lineage 확인 |
| 4 | 4개 화면, SQL 필터, 상세 조회, coverage 표시 | 가격·소셜·상태를 설명할 수 있는 데모 |
| 5 | 수작업 검토, 장애·삭제·백업 복구, 성능 측정 | 결과와 한계가 포함된 validation report |
| 6 | 결함 수정, 재현 안내, 발표와 최종 보고 | 새 환경에서 재현 가능한 시연 절차 |

팀원별 담당과 공식 마감일은 TBD다. 초기에는 사람 이름 대신 수집·데이터 모델/ETL·분석/검증·대시보드 역할로 작업을 분배하고, 팀 구성이 확인되면 담당자를 채운다. 유료 서비스나 이미지·LLM 기능 추가는 핵심 흐름의 인수 기준 충족 이후에 검토한다.

## 8. 문서와 구현 상태 구분

문서 배포 전에는 내부 링크, JSON 예시, 데이터 수치, 역할·용어·일정의 일관성을 검토한다. 구현 시에는 이 문서의 시나리오를 실제 결과와 연결하는 검증 보고서를 추가한다. 데이터가 없어서 실행하지 못한 검증은 skipped와 사유를 기록한다. 문서 작성·정적 검토 완료를 파이프라인 통합 테스트 통과로 보고하지 않는다.
